# Архитектура доступа HOS Service к KB v0.1

**Статус:** архитектурная гипотеза для проверки  
**Версия:** 0.1

## 1. Цель

Обеспечить любому пользователю HOS Service доступ к одной актуальной Canonical KB независимо от общего размера базы и количества исходных Markdown-файлов.

## 2. Источник истины

Единственным нормативным источником является Canonical KB в GitHub (`main`).

Индексы, Runtime-представления, поисковые базы и иные технические представления являются производными и должны быть полностью воспроизводимы из Canonical KB.

## 3. Общая схема

```text
Canonical KB / GitHub main
          ↓
автоматическая индексация
          ↓
HOS Knowledge Service
          ↓
HOS Service / LLM
          ↓
пользователи
```

Пользователю не требуется получать всю KB в контекст LLM. Knowledge Service должен предоставлять только необходимые канонические объекты или релевантные фрагменты.

## 4. Два режима доступа

### 4.1. Детерминированный retrieval

Применяется, когда запрашивается конкретный канонический объект или конкретная версия: диагностический протокол, определение, формальная спецификация и т. п.

Knowledge Service обязан вернуть именно запрошенный объект, а не наиболее семантически похожий текст.

### 4.2. Семантический retrieval

Применяется для аналитических, объяснительных и исследовательских запросов, когда заранее неизвестен конкретный объект KB.

Knowledge Service возвращает релевантные фрагменты с сохранением связи с каноническими источниками.

Оба режима могут использоваться совместно в рамках одного запроса.

## 5. Архитектурный инвариант

Если пользователь требует конкретный канонический объект, а Knowledge Service не может его получить, LLM не должна реконструировать этот объект по памяти, контексту или аналогии.

Отсутствие объекта должно быть явно зафиксировано как ошибка доступа или отсутствие знания.

## 6. Обновление знания

Содержательные изменения вносятся только в Canonical KB. После изменения `main` производные поисковые представления должны автоматически обновляться.

Ручное распространение копий KB между пользователями HOS Service не является частью целевой архитектуры.

## 7. Статус HOS_KB_Runtime.md

`HOS_KB_Runtime.md` является временным compatibility artifact для экспериментов с ChatGPT Shared Project.

Он не является целевой формой базы знаний HOS Service и не является самостоятельной версией Canonical KB.

## 8. Что v0.1 намеренно не определяет

Версия 0.1 не фиксирует конкретную СУБД, vector store, embedding-модель, язык программирования, API framework или облачную платформу.

Эти решения должны приниматься после проверки контракта доступа к знанию, а не определять архитектуру HOS заранее.

## 9. Проверяемые требования

1. Если в Canonical KB существует объект X версии Y, Knowledge Service должен детерминированно предоставить LLM именно X(Y).
2. Для семантического запроса Knowledge Service должен предоставлять релевантные фрагменты с трассировкой до канонического источника.
3. Обновление Canonical KB должно приводить к воспроизводимому обновлению производных поисковых представлений.
4. Ошибка retrieval конкретного канонического объекта не должна приводить к его реконструкции LLM.

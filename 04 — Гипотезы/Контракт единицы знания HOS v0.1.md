# Контракт единицы знания HOS v0.1

**Статус:** архитектурная гипотеза для проверки  
**Версия:** 0.1

## 1. Назначение

Контракт задаёт минимальные требования, позволяющие HOS Knowledge Service получать знание из Canonical KB воспроизводимо и с сохранением происхождения источника.

Контракт является инфраструктурным и не вводит новые сущности в содержательную модель HOS.

## 2. Канонический объект и поисковый фрагмент

Необходимо различать:

**Канонический объект** — зафиксированный автором документ Canonical KB.

**Поисковый фрагмент** — технически выделенная часть канонического объекта, создаваемая для retrieval.

Поисковый фрагмент не становится самостоятельным знанием HOS. Нормативным остаётся исходный канонический объект.

## 3. Минимальный контракт канонического объекта

Каждый канонический документ должен иметь следующие атрибуты:

```text
id
source_path
title
status
source_sha
retrieval_mode
```

### id

Стабильный идентификатор канонического объекта. Не должен изменяться при переименовании или перемещении файла.

### source_path

Текущий физический путь документа в Canonical KB.

### title

Человекочитаемое название документа.

### status

Статус знания в архитектуре HOS: например, канон, гипотеза, эмпирика, техника. Конкретный допустимый словарь статусов данным контрактом пока не нормируется.

### source_sha

Идентификатор конкретной редакции исходного текста. Позволяет установить, из какой версии Canonical KB получено знание.

### retrieval_mode

Допустимые значения:

```text
whole_document
fragment
```

`whole_document` применяется, когда полнота, последовательность или структура документа являются частью его нормативного смысла.

`fragment` допускает техническое разбиение документа для семантического retrieval.

## 4. Минимальный контракт поискового фрагмента

```text
parent_id
fragment_id
text
location
source_sha
```

`parent_id` связывает фрагмент с каноническим объектом.  
`fragment_id` идентифицирует фрагмент внутри производного поискового представления.  
`text` содержит извлекаемый текст.  
`location` позволяет определить положение текста в исходном объекте.  
`source_sha` фиксирует редакцию исходного документа.

Embeddings и иные поисковые индексы являются техническими производными и не относятся к содержательной модели HOS.

## 5. Исполняемые протоколы

Документы, в которых порядок, полнота или точность последовательности являются частью метода, не должны извлекаться произвольным chunking.

К этому классу относятся, в частности, диагностические протоколы.

Для `Экспресс-тест уровня развития v0.1` должен использоваться:

```text
retrieval_mode: whole_document
```

Это предотвращает ситуацию, когда LLM получает только отдельные семантически релевантные части протокола и пытается восстановить недостающие элементы.

## 6. Инвариант происхождения знания

Любой текст, переданный LLM как знание HOS, должен быть трассируем до конкретного канонического объекта и конкретной редакции этого объекта.

Цепочка происхождения должна иметь вид:

```text
retrieved text
    ↓
fragment (если применимо)
    ↓
canonical object id
    ↓
source_path
    ↓
source_sha
```

## 7. Правило отказа

Если требуемый канонический объект или его необходимая версия недоступны, Knowledge Service должен сообщить об отсутствии результата.

LLM не должна подменять отсутствующий канонический объект реконструкцией по памяти или генерацией аналога.

## 8. Что v0.1 намеренно не вводит

Контракт пока не вводит отдельные поля `knowledge_type`, confidence, граф отношений, классы онтологии и другие метаданные, пока не выявлена задача, для которой они необходимы.

Разметка всех документов вручную также не является требованием v0.1. Техническое выделение фрагментов может выполняться автоматически, если `retrieval_mode` это допускает.

## 9. Проверяемое требование

Если в Canonical KB существует объект X редакции Y, HOS Knowledge Service должен быть способен:

- детерминированно получить X(Y), когда объект известен;
- получить релевантные фрагменты X(Y), когда разрешён фрагментный retrieval;
- для любого результата указать его канонический источник и редакцию;
- не генерировать замену X(Y), если retrieval завершился неудачей.

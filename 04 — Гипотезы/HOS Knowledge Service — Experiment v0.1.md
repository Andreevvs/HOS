# HOS Knowledge Service — Experiment v0.1

**Статус:** архитектурный эксперимент / гипотеза для проверки  
**Версия:** 0.1

## 1. Цель эксперимента

Проверить гипотезу:

> Внешний слой знания может надёжно обеспечивать LLM актуальными знаниями Canonical KB без загрузки всей KB в контекст модели.

Эксперимент не является реализацией полноценного HOS Service и не должен включать диагностику человека, расчёт ИУТ, пользовательские профили или рекомендательную систему.

## 2. Минимальная архитектура

```text
Canonical KB / GitHub
        ↓
    индексатор
        ↓
HOS Knowledge Service
   ↙             ↘
exact()         search()
   ↓             ↓
whole document  fragments
        ↓
       LLM
```

## 3. Минимальные функции

### exact(id, version?)

Детерминированно возвращает конкретный канонический объект.

Результат должен содержать как минимум:

```text
id
source_path
source_sha
text
```

Если объект или требуемая версия не найдены, функция должна вернуть явный `not found`. Семантически похожий объект не является допустимой заменой.

### search(query)

Возвращает несколько релевантных фрагментов Canonical KB.

Каждый результат должен сохранять provenance как минимум до:

```text
parent_id
source_path
source_sha
location
text
```

## 4. Ограничения v0.1

В эксперимент намеренно не входят:

- полноценный интерфейс HOS Service;
- диагностика пользователя;
- расчёт ИУТ;
- персональные рекомендации;
- агентная архитектура Knowledge / Reasoning / Critic;
- выбор окончательной технологической платформы;
- ручное создание отдельной базы знаний, расходящейся с Canonical KB.

Индекс должен быть воспроизводим из Canonical KB.

## 5. Evals

### E1 — Exact retrieval

Запросить `Экспресс-тест уровня развития v0.1`.

**Критерий успеха:** возвращён полный канонический документ требуемой редакции, без реконструкции отсутствующих частей.

### E2 — Version propagation

Изменить тестовый канонический документ в `main`, перестроить индекс и повторить retrieval.

**Критерий успеха:** сервис возвращает новую редакцию и соответствующий новый `source_sha`.

### E3 — Semantic retrieval

Задать содержательный запрос, например:

> Как в HOS связаны уровни развития и метакомпетенции?

**Критерий успеха:** сервис находит релевантные фрагменты без предварительного указания имён файлов и для каждого сохраняет provenance.

Качество этого теста оценивается отдельно; сам факт выдачи результатов не считается достаточным доказательством качества semantic retrieval.

### E4 — Missing canonical object

Запросить заведомо отсутствующий объект, например `Экспресс-тест уровня развития v9.7`.

**Критерий успеха:** явный `not found`; сервис и LLM не создают аналог и не подменяют версию.

### E5 — Provenance

Для каждого результата retrieval проверить возможность установить канонический Markdown-документ и конкретную редакцию.

**Критерий успеха:** происхождение каждого результата однозначно трассируется до `source_path` и `source_sha`.

## 6. Критерий подтверждения гипотезы

Гипотеза v0.1 считается предварительно подтверждённой, если E1, E2, E4 и E5 проходят детерминированно, а E3 показывает практически пригодное качество semantic retrieval на заранее зафиксированном наборе запросов.

Единичный успешный запуск не считается достаточным подтверждением надёжности.

## 7. Роль Codex

Codex может использоваться как инженерная среда для реализации прототипа, автоматизации evals и проверки изменений.

Codex не определяет содержательную архитектуру HOS. Реализация должна следовать утверждённым контрактам:

- `Архитектура доступа HOS Service к KB v0.1`;
- `Контракт единицы знания HOS v0.1`;
- настоящий эксперимент v0.1.

## 8. Следующая гипотеза

Только после успешной проверки Knowledge Service имеет смысл отдельно проверять, даёт ли агентное разделение `Knowledge / Reasoning / Critic` измеримое преимущество перед одной LLM с инструментами.

Это не является частью Experiment v0.1.

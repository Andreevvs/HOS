# HOS Service — Express Diagnostic E2E Experiment v0.1

Минимальный внешний прототип выполняет канонический экспресс-тест через цепочку
`web UI → ProtocolExecutor → KnowledgeService.exact() → Canonical KB`. Приложение не
содержит копии вопросов: при каждом новом сеансе `ProtocolExecutor` получает полный
`whole_document`, проверяет структуру Q1–Q12 и сохраняет снимок `protocol_text` вместе
с `protocol_id`, `source_path` и `source_sha`. Уже начатый сеанс больше не обращается к
изменяемому источнику и потому остаётся привязанным к исходной редакции.

## Локальный запуск

Требуется Python 3.10+, внешних зависимостей нет.

```bash
python -m diagnostic_service.web
```

Открыть `http://localhost:8080`.

Проверки:

```bash
python -m unittest discover -v
```

## Технические решения

* стандартные `http.server` и Fetch API — минимальный заменяемый web-слой;
* сессии хранятся в памяти процесса и имеют состояния `initialized`, `in_progress`,
  `awaiting_feedback`, `completed`, `error`;
* Markdown-парсер проверяет ровно 12 последовательных секций вопросов и извлекает из
  канонического документа вводное сообщение, названия Q1–Q12 и три feedback-пункта;
* ответы принимаются только как целые числа 0–10; иной ввод не меняет состояние;
* UI показывает только текущий вопрос: следующий вопрос заменяет предыдущий;
* после Q12 executor выдаёт утверждённую структуру результата: вектор, предварительную
  гипотезу L, ориентировочный диапазон ИУТ, уверенность, сильные/контрастные показатели,
  комментарий о текущей жизни и ограничение экспресс-оценки;
* ИУТ не считается средним или взвешенной суммой; L5 не подтверждается, L6 не
  диагностируется;
* HTTP API состоит из `POST /sessions` и `POST /sessions/{session_id}/messages`;
  web UI не получает прямого доступа к файлам KB.

Минимальная интерпретация детерминирована. Границы 0–3 / 4–6 / 7–10 взяты из
канонической технической гипотезы v0.1. Разрешение степени уверенности в executor —
техническая эвристика приложения, а не новый закон HOS.

## Текущие ограничения

### Методология HOS

* 12 самооценок не подтверждают прохождение кризисов; особенно это ограничивает
  различение L4/L5 и не позволяет диагностировать L6.
* Канон требует степень уверенности, но пока не задаёт отдельной формальной шкалы её
  вычисления. Прототип поэтому использует явную техническую эвристику.
* Выбор 3 высоких и 3 низких показателей — техническое правило отображения внутри
  разрешённого каноном диапазона 2–4, а не самостоятельная методика HOS.
* Не определены отдельные правила для отказа от feedback; прототип сохраняет три
  текстовых ответа.

### Knowledge architecture

* Исполняемые части Markdown не имеют машиночитаемой schema/version; parser опирается
  на заголовки и списки канонического документа.
* Registry фиксирует `whole_document`, но не объявляет отдельный тип «исполняемый
  протокол».
* Knowledge Service не является историческим хранилищем старых редакций; pinning
  активного сеанса обеспечивается сохранённым snapshot.

### Application / deployment

* Сессии in-memory и исчезают при рестарте.
* Нет production TLS, rate limiting, observability, privacy controls и распределённого
  хранения.
* Публичный внешний URL пока не является частью проверенного E2E; локальный HTTP
  прототип и ручное прохождение проверены отдельно.

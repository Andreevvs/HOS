# HOS Service — Express Diagnostic E2E Experiment v0.1

Минимальный внешний прототип выполняет канонический экспресс-тест через цепочку
`web UI → ProtocolExecutor → KnowledgeService.exact() → Canonical KB`. Приложение не
содержит копии вопросов: при каждом новом сеансе `ProtocolExecutor` получает полный
`whole_document`, проверяет структуру Q1–Q12 и сохраняет снимок `protocol_text` вместе
с `protocol_id`, `source_path` и `source_sha`. Уже начатый сеанс больше не обращается к
изменяемому источнику и потому остаётся привязанным к исходной редакции.

## Локальный и внешний запуск

Требуется Python 3.10+, внешних зависимостей нет.

```bash
python -m diagnostic_service.web
```

Открыть `http://localhost:8080`. Для внешнего эксперимента этот же процесс можно
запустить на машине с доступным извне портом 8080 или поставить перед ним заменяемый
HTTPS reverse proxy/tunnel. Сервер слушает `0.0.0.0:8080`; production-инфраструктура,
TLS, авторизация и долговременное хранение намеренно не входят в эксперимент.

Проверки:

```bash
python -m unittest discover -v
```

## Технические решения

* стандартные `http.server` и Fetch API выбраны как минимальный заменяемый web-слой;
* сессии хранятся в памяти процесса и имеют состояния `initialized`, `in_progress`,
  `awaiting_feedback`, `completed`, `error`;
* Markdown-парсер проверяет ровно 12 последовательных секций вопросов и извлекает из
  канонической интерпретации названия показателей, оговорку и вводное сообщение;
* ответы принимаются только как целые числа 0–10; любой иной ввод оставляет курсор и
  ответы неизменными и снова показывает текущий канонический вопрос;
* итоговая формулировка детерминирована и не требует LLM: три максимальных и три
  минимальных показателя выбираются со стабильным разрешением равенств по номеру Q;
* HTTP API состоит из `POST /sessions` и
  `POST /sessions/{session_id}/messages`; UI не получает доступ к файлам KB.

Это детали приложения, а не новые сущности или архитектурные решения HOS. Интерфейс
интерпретатора можно позднее заменить LLM-adapter, не меняя retrieval и состояние.

## Обнаруженные проблемы

### HOS methodology gap

* Канонический документ не задаёт точной реакции на просьбу пропустить вопрос,
  промежуточную интерпретацию, посторонний вопрос или смену шкалы. Прототип применяет
  минимальный технический отказ и повторяет текущий вопрос, не расширяя диагностику.
* Не определены правила разрешения равных значений, точное число выбираемых показателей
  внутри разрешённого диапазона 2–4 и детерминированный словарь «конфигураций».
  Прототип явно фиксирует техническое правило `3 + 3`, но не объявляет его методикой.
* Не определено, валидировать ли числом первый feedback и как обрабатывать отказ от
  любого из трёх пунктов обратной связи. Прототип сохраняет три текстовых сообщения.

### Knowledge architecture gap

* Исполняемые части Markdown не имеют машиночитаемой схемы. Парсер вынужден опираться
  на русские заголовки и оформление списка, поэтому корректное содержательное
  изменение формата может привести к контролируемому отказу до обновления executor.
* Registry фиксирует `whole_document`, но не объявляет тип объекта «исполняемый
  протокол» или его версию схемы; это не добавлялось молча в контракт.
* Текущий Knowledge Service проверяет актуальность файла и умеет получить только
  построенную редакцию. Хранение полного текста в session решает pinning внутри
  процесса, но `exact(id, old_sha)` после rebuild не является историческим хранилищем.

### Application implementation gap

* In-memory сессии исчезают при рестарте и не подходят для нескольких процессов.
* Прототип не имеет TLS, rate limiting, мониторинга, accessibility-аудита и защиты
  персональных данных production-уровня.
* Итоговый естественный язык минимален и детерминирован; его качество требует отдельной
  пользовательской проверки, но структурные запреты тестируются автоматически.

# HOS Service — Full IUT Diagnostic v0.1 — Codex Task

**Статус:** техническое задание на экспериментальную реализацию сценария №2.  
**Канонический источник методики:** `03 — Диагностика/ИУТ — измерение.md`, версия и SHA фиксируются Knowledge Service при старте сеанса.  
**Архитектурная спецификация:** `04 — Гипотезы/HOS Service — Полная диагностика ИУТ v0.1.md`.

## 1. Цель

Расширить HOS Service вторым пользовательским сценарием — полной диагностикой ИУТ — не изменяя методику HOS и не превращая банк вопросов в линейную анкету.

Пользователь должен открыть приложение, выбрать один из двух режимов и пройти выбранную диагностику:

- **Экспресс-тест** — существующий сценарий;
- **Полный тест ИУТ** — новое адаптивное биографически-ситуационное интервью.

## 2. UI

Стартовый маршрут `/` показывает HOS и две основные кнопки:

- `Экспресс-тест` → `/express`;
- `Полный тест ИУТ` → `/full`.

Существующий экспресс-тест переносится/маршрутизируется на `/express` без изменения его диагностической логики.

`/full` предоставляет диалоговый интерфейс полного интервью. В отличие от экспресс-теста, предыдущий контекст интервью должен сохраняться визуально или быть доступен пользователю: полный тест зависит от биографического контекста и уточнений.

## 3. Получение канона

При старте полного теста приложение обязано получить через Knowledge Service методом `exact()` объект канонического `03 — Диагностика/ИУТ — измерение.md`.

Сеанс фиксирует минимум:

- canonical object id;
- `source_path`;
- `source_sha`;
- версию протокола, если она извлечена из документа;
- точный текст канонического snapshot.

Snapshot pinning обязателен: изменение KB во время интервью не меняет уже начатый сеанс. Если exact retrieval отсутствует, stale или не имеет достаточного provenance, полный тест не запускается (fail closed).

В код приложения нельзя копировать банк диагностических вопросов как независимый источник истины.

## 4. Архитектура исполнения

Ввести отдельный компонент `FullIUTInterview` (название модуля/класса может быть технически уточнено без изменения архитектуры).

Он не является вторым `ProtocolExecutor` с последовательным счётчиком вопросов.

Разделение ответственности:

### Детерминированный оркестратор

Отвечает за:

- жизненный цикл сеанса;
- exact retrieval и pinning;
- сохранение истории вопросов/ответов;
- хранение текущего диагностического состояния;
- запрет преждевременного раскрытия предполагаемого уровня;
- последовательность допустимых зон проверки;
- fail-closed ограничения;
- формирование итогового ответа только после завершения диагностики;
- provenance результата.

### Интерпретирующий LLM-слой

Отвечает за:

- интерпретацию свободного биографического ответа;
- выбор следующего вопроса или уточнения из рамок канонического банка/принципа интервью;
- разворачивание абстрактного ответа по схеме `факт → контекст → мотив → длительность → последствия → цена выбора → проверка реальностью`;
- оценку свидетельств за/против прохождения кризиса;
- выявление противоречий;
- предложение остановки, когда новые вопросы дают существенно меньше информации.

LLM не имеет права создавать новые кризисы, уровни, диапазоны ИУТ или диагностические критерии, отсутствующие в каноне.

## 5. Диагностическое состояние

Минимально хранить для Кр1–Кр6 состояние:

- `unexamined`;
- `uncertain`;
- `supported`;
- `contradicted`.

Это технические состояния приложения, а не новые сущности теории HOS.

Для каждого проверяемого кризиса хранить ссылки на свидетельства из диалога: факты/ответы, поддерживающие вывод, противоречащие ему или оставляющие неопределённость.

Не считать отдельный ответ доказательством уровня.

## 6. Адаптивный маршрут

Оркестратор должен обеспечивать каноническую последовательность:

1. входной скрининг;
2. при нормальном автономном функционировании основная плотность Кр3↔Кр4;
3. если Кр4 не подтверждён — не уходить подробно в Кр5–Кр6;
4. если Кр4 подтверждён — перейти к Кр4↔Кр5;
5. только после подтверждения Кр5 — Кр5↔Кр6;
6. при противоречиях возвращаться к нижним кризисам;
7. деятельностная состоятельность используется для проверки фактической реализации и reality check;
8. остановиться, когда дальнейшие вопросы существенно не увеличивают диагностическую определённость.

Кр7 не операционализирован. Не придумывать его диагностику.

## 7. Критерий кризиса

Для Кр1–Кр6 использовать только канонический общий критерий устойчивой интеграции:

1. воспроизводимость;
2. преодоление структурного ограничения предыдущего уровня;
3. переносимость.

Специфические новообразования кризисов брать только из canonical snapshot.

Не вводить числовые пороги длительности, частоты или количества примеров: в каноне они пока не установлены.

## 8. Ограничение v0.1

Канон не содержит полностью детерминированного автомата принятия решения `Крn подтверждён` из набора текстовых ответов. Поэтому v0.1 не должна маскировать LLM-интерпретацию под формальный закон HOS.

Каждый итоговый кризисный вывод должен иметь trace к конкретным свидетельствам интервью и каноническому критерию. При недостаточности данных результат должен оставаться неопределённым, а не разрешаться эвристическим баллом.

## 9. Итог диагностики

Итоговый экран/ответ должен следовать каноническому формату:

- **Подтверждённый уровень:** ...
- **Диапазон ИУТ/УРЛ:** ...
- **Следующий кризис:** ...
- **Статус перехода:** ...
- **Положение внутри диапазона:** только при достаточном основании; иначе `не операционализировано`;
- **Подтверждающие свидетельства:** ...
- **Противоречащие/неопределённые свидетельства:** ...
- **Главный вопрос дальнейшей проверки:** ...

Не выдавать псевдоточное значение ИУТ.

## 10. Acceptance criteria

E1. `/` содержит две кнопки и корректно маршрутизирует `/express` и `/full`.

E2. Существующий экспресс-тест продолжает работать на `/express` без регрессии методики.

E3. `/full` запускает отдельный тип диагностического сеанса.

E4. Полный сеанс начинается только после успешного `exact()` канонического `ИУТ — измерение.md`.

E5. В сеансе сохранены `source_path`, `source_sha` и canonical snapshot; начатый сеанс не меняется после изменения KB.

E6. При недоступном/невалидном exact canonical object полный тест контролируемо не запускается.

E7. Банк вопросов не исполняется как обязательные вопросы 1→50.

E8. Абстрактный ответ допускает адаптивное уточнение по канонической биографически-ситуационной схеме.

E9. До финала пользователю не сообщается промежуточный предполагаемый L/ИУТ.

E10. Переход к подробной проверке Кр5 невозможен, пока Кр4 не получил достаточной поддержки; Кр6 — пока не поддержан Кр5.

E11. Противоречащие свидетельства сохраняются и могут вернуть интервью к нижележащему кризису.

E12. Кр7 не диагностируется.

E13. Итог содержит канонические поля результата и evidence trace.

E14. Итог не содержит псевдоточного ИУТ внутри диапазона без отдельного диагностического основания.

E15. Изменение canonical file отражается в новом сеансе после rebuild Knowledge Service, но не меняет старый pinned session.

E16. Автоматические тесты покрывают routing, exact/fail-closed, pinning, последовательность кризисов, отсутствие линейного 50-вопросного исполнения и формат финального результата.

## 11. Не делать в этом эксперименте

- Не формализовать заново HOS.
- Не добавлять новые уровни/кризисы/метакомпетенции.
- Не вычислять точное ИУТ по самодельной формуле.
- Не превращать LLM confidence в каноническую шкалу HOS.
- Не менять канонический банк вопросов ради удобства программирования.
- Не объединять executor экспресс-теста и полный адаптивный interview engine в один универсальный автомат, если это стирает различие методик.

## 12. Definition of Done

Эксперимент считается локально реализованным, когда E1–E16 покрыты тестами и ручной браузерный проход показывает оба пользовательских сценария. Это ещё не доказывает внешнюю доступность сервиса: публичный URL проверяется отдельно.

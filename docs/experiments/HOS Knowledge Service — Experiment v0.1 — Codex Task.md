# ТЗ для Codex: HOS Knowledge Service — Experiment v0.1

**Статус:** инженерное задание для архитектурного эксперимента  
**Версия:** 0.1

## 1. Репозиторий и обязательные источники

Работай с репозиторием `Andreevvs/HOS`, ветка `main`.

Перед реализацией полностью прочитай:

1. `04 — Гипотезы/Архитектура доступа HOS Service к KB v0.1.md`
2. `04 — Гипотезы/Контракт единицы знания HOS v0.1.md`
3. `04 — Гипотезы/HOS Knowledge Service — Experiment v0.1.md`

Эти документы имеют приоритет над предположениями исполнителя и техническими удобствами реализации.

## 2. Цель

Реализовать минимальный прототип `HOS Knowledge Service — Experiment v0.1`, проверяющий, может ли LLM надёжно получать актуальное знание Canonical KB без загрузки всей KB в контекст.

Это не реализация полноценного HOS Service.

## 3. Жёсткие ограничения

- Не изменять содержательную модель HOS ради удобства реализации.
- Не добавлять новые сущности HOS.
- Не изменять определения, уровни развития, линии развития, метакомпетенции и диагностические методики.
- Не повышать статус гипотез до канона.
- Не реконструировать отсутствующее знание.
- Не превращать техническую структуру индекса в онтологию HOS.
- Если реализация требует изменения архитектурного контракта, остановиться и описать проблему вместо самостоятельного изменения контракта.

Главное правило:

> Если возникает выбор между «изменить HOS, чтобы код заработал» и «сообщить об архитектурной проблеме», выбрать второе.

## 4. Источник истины

Источник истины — Canonical KB в `main`.

Не использовать `runtime/HOS_KB_Runtime.md`, `HOS_KB_Runtime.md` или иное Runtime-представление как источник знания.

Индекс и другие технические представления должны быть воспроизводимы из Canonical KB.

## 5. Минимальные интерфейсы

### `exact(id, version=None)`

Детерминированно возвращает конкретный канонический объект.

Минимальный результат:

```text
id
source_path
source_sha
text
```

Если объект или требуемая версия отсутствуют — вернуть явный `not_found`.

Запрещено заменять отсутствующий объект ближайшим семантически похожим документом.

### `search(query)`

Возвращает релевантные фрагменты Canonical KB.

Минимальный результат каждого фрагмента:

```text
parent_id
source_path
source_sha
location
text
```

Количество результатов должно быть конфигурируемым.

## 6. Индексация Canonical KB

Индексировать активную Canonical KB из `main`.

Существующие правила исключения Runtime-builder можно использовать как подсказку, но необходимо проверить их по текущему состоянию репозитория.

`99 — Архив/**`, `07 — Экспорт/**` и иные явно архивные/экспортные представления не должны становиться активным знанием.

Для каждого результата сохранять provenance до исходного Markdown-файла и его редакции.

## 7. Временный registry для Experiment v0.1

Текущая Canonical KB ещё не содержит систематически назначенных стабильных `id` и `retrieval_mode` для всех документов.

Не изменять автоматически 100+ документов ради эксперимента.

Для Experiment v0.1 разрешён внешний технический manifest/registry, связывающий необходимые тестовые объекты с:

```text
id
source_path
retrieval_mode
```

Registry является временной инфраструктурой эксперимента и не является новой сущностью содержательной модели HOS.

Duplicate `id` должен считаться ошибкой.

## 8. Whole-document retrieval

Документ:

`03 — Диагностика/Экспресс-тест уровня развития v0.1.md`

должен иметь:

```text
retrieval_mode: whole_document
```

`exact()` должен возвращать полный исходный документ. Chunking не должен изменять его нормативное содержание или использоваться как замена полного протокола.

## 9. Fragment retrieval

Для документов с `retrieval_mode: fragment` сначала использовать естественную Markdown-структуру — заголовки/секции, затем при необходимости технические ограничения размера.

Каждый фрагмент обязан сохранять provenance.

Не создавать семантическую онтологию HOS в рамках chunking.

## 10. Semantic search

Выбрать минимально достаточный механизм semantic retrieval.

Конкретная embedding-модель, vector store или иной поисковый механизм не являются архитектурным решением HOS v0.1.

Механизм поиска должен быть заменяем без изменения Canonical KB и контрактов `exact()` / `search()`.

Выбор технологии и его причины описать в техническом README.

## 11. Автоматизированные evals

### E1 — Exact retrieval

Запросить `Экспресс-тест уровня развития v0.1`.

Успех: возвращён полный канонический документ требуемой редакции.

### E2 — Version propagation

В рамках теста временно изменить тестовый канонический документ, перестроить индекс и повторить retrieval.

Успех: получена новая редакция и новый `source_sha`.

Тест не должен оставлять содержательных изменений в Canonical KB после завершения.

### E3 — Semantic retrieval

Фиксированный запрос:

`Как в HOS связаны уровни развития и метакомпетенции?`

Оценивать релевантность найденных источников, а не только наличие непустого результата. Для каждого результата проверить provenance.

### E4 — Missing canonical object

Запросить:

`Экспресс-тест уровня развития v9.7`

Успех: `not_found`, без реконструкции, подмены версии или семантически похожего аналога.

### E5 — Provenance

Для каждого результата retrieval проверить наличие и корректность как минимум `source_path` и `source_sha`.

## 12. Негативные тесты

Добавить тесты как минимум для:

- неизвестного `id`;
- пустого semantic query;
- отсутствующего или переименованного `source_path`;
- duplicate `id` в registry;
- изменения исходного документа после построения индекса;
- конфликта provenance / stale index.

При конфликте происхождения знания система должна выдавать явную ошибку, а не молча использовать устаревшее знание.

## 13. Что не реализовывать

В Experiment v0.1 не реализовывать:

- пользовательский интерфейс HOS;
- аккаунты пользователей;
- диагностику человека;
- расчёт ИУТ или СУТ;
- персонализацию;
- долговременную память пользователя;
- `Knowledge Agent`;
- `Reasoning Agent`;
- `Critic Agent`;
- multi-agent orchestration;
- production deployment;
- billing;
- преждевременную оптимизацию производительности.

## 14. Структура реализации

Код должен позволять независимо заменить как минимум:

- source loader;
- chunker;
- semantic index;
- retrieval layer.

Не создавать абстракции, которые не нужны для выполнения эксперимента.

## 16. Критерии приёмки

Эксперимент считается технически выполненным, если:

- `exact()` воспроизводимо возвращает полный правильный протокол;
- отсутствующий объект даёт `not_found`;
- изменение источника обнаруживается;
- provenance проверяется;
- semantic retrieval практически полезен на фиксированных запросах;
- для работы не требуется монолитный Runtime;
- Canonical KB не получила содержательных изменений ради реализации.

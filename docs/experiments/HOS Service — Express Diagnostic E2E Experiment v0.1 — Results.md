## Категории проблем

### HOS methodology gap

Канон не фиксирует формулировки отказов при отклонениях, tie-breaking при равных
показателях, точный выбор количества из диапазона 2–4 и протокол невалидной/неполной
обратной связи. Они не исправлялись в Canonical KB; применены только явно описанные в
техническом README минимальные правила приложения.

### Knowledge architecture gap

Исполняемый Markdown не имеет machine-readable schema/version; registry не содержит
типа исполняемого объекта; Knowledge Service не хранит старые редакции для последующего
`exact(id, old_sha)`. Pinning обеспечено сохранением retrieved snapshot в session, без
изменения существующего контракта.

### Application implementation gap

Сессии volatile/in-memory; отсутствуют production TLS, privacy controls, distributed
storage и observability. Детерминированная интерпретация выполняет структурный
контракт, но её естественный язык ещё не оценивался внешними пользователями.

## Вывод

Главный критерий эксперимента подтверждён в пределах локального E2E: web-пользователю
не нужен доступ к KB, изменение тестовой Canonical KB попадает в новый сеанс без
изменения кода, а начатый сеанс не меняется скрыто. Публичное размещение и реальная
пользовательская проверка остаются отдельным application/deployment этапом.

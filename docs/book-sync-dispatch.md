# Автоматический запуск синхронизации книги HOS → hos-web

## Как работает

Workflow `.github/workflows/dispatch-book-sync.yml` запускается на `push` в `main` репозитория `Andreevvs/HOS`. Он сравнивает полные Git-состояния каталога `Сайт проекта HOS/Книга/Части/` между `before` и `after` события. Проверяется весь push, включая несколько коммитов, добавления, изменения, удаления и переименования. Изменение, отменённое в пределах одного push, не запускает синхронизацию.

Фильтр GitHub `paths` не используется: его ограничения на размер diff не должны приводить к пропуску книги. Проверяющий workflow запускается и для других изменений HOS, но если каталог книги не изменился, он завершится **до запроса App token и без вызова hos-web**. У исходного workflow нет общей concurrency-группы: GitHub может заменить ожидающий запуск более новым, что могло бы потерять событие книги при последующем постороннем push.

Если каталог изменился, отдельный GitHub App выдаёт временный installation token только для `Andreevvs/hos-web` с `Actions: write`. Скрипт отправляет фиксированный запрос `workflow_dispatch` к `sync-book.yml`, `ref: main`. Входные параметры события не могут подменить репозиторий, имя workflow или ветку. Redirect HTTP-запроса запрещён, чтобы заголовок авторизации не пересылался на другой адрес.

Целевой `sync-book.yml` не меняется. Он продолжает читать актуальную ветку по умолчанию HOS через **HOS Book Reader**, сохраняет ручной запуск, создаёт/обновляет PR только при изменениях и ничего не объединяет автоматически. Тексты и метаданные копируются по прежним правилам; отсутствующие файлы не удаляются. Фильтрация `draft`/`published`/`hidden` не меняется. Проверка исходного каталога реагирует на любые файлы внутри него, но целевой скрипт копирует только Markdown: если итоговое содержимое книги не изменилось, PR не создаётся.

При нескольких близких push каждый проверяется независимо; целевой workflow использует свою существующую concurrency-группу и читает актуальную книгу, а не обязательно коммит, вызвавший уведомление. Отправка dispatch не означает завершения синхронизации — её результат нужно смотреть в Actions репозитория hos-web.

## Настройки GitHub, которые выполняются вручную

### 1. Создать отдельный GitHub App

В настройках аккаунта/организации откройте **Developer settings → GitHub Apps → New GitHub App**. Например, назовите приложение **HOS Web Sync Dispatcher** (имя должно быть свободно).

- Homepage URL: URL репозитория HOS.
- Webhook: отключён; webhook URL и подписки на события не нужны.
- Repository permissions: **Actions: Read and write**. **Metadata: Read-only** предоставляется GitHub автоматически. Остальные разрешения не выдавайте.
- Если приложение нужно только этому аккаунту, выберите установку только на этот аккаунт.

Установите приложение на аккаунт **Andreevvs**, выберите **Only select repositories → hos-web**. Не добавляйте HOS и другие репозитории к установке. Создайте private key и сохраните App ID (не Client ID и не Installation ID).

GitHub не позволяет ограничить `Actions: write` одним workflow: App получает управление Actions в пределах hos-web, включая другие workflows. Права записи содержимого и Pull requests этому App не нужны. Права и установку существующего **HOS Book Reader не меняйте**.

### 2. Добавить конфигурацию именно в HOS

Откройте **Andreevvs/HOS → Settings → Secrets and variables → Actions**:

| Тип | Имя | Значение |
| --- | --- | --- |
| Repository variable | `HOS_WEB_DISPATCH_APP_ID` | App ID нового приложения |
| Repository secret | `HOS_WEB_DISPATCH_APP_PRIVATE_KEY` | Полное содержимое PEM private key нового приложения |

Приватный ключ вводится только в GitHub Secrets. Не добавляйте его, installation token или их значения в файлы, PR, логи и аргументы командной строки. Короткоживущий токен создаётся и маскируется action, передаётся только нужному шагу через окружение и отзывается post-шагом action.

Поскольку workflow в HOS сможет запускать Actions приватного hos-web, защитите `main` в HOS от непроверенных изменений, особенно `.github/workflows/` и `scripts/dispatch_book_sync.py`, и ограничьте круг пользователей с правом записи. Workflow не запускается на pull requests или в forks. Не используйте `pull_request_target` для передачи этого секрета коду PR.

### 3. Проверить готовность hos-web

- `sync-book.yml` должен быть в `main` и иметь `workflow_dispatch`; Actions должны быть включены.
- Существующие `HOS_READ_APP_ID` и `HOS_READ_APP_PRIVATE_KEY` в hos-web и доступ HOS Book Reader должны быть настроены как прежде.
- В hos-web сохраните разрешение Actions создавать PR. Новый App сам PR не создаёт: это делает прежний workflow своим `GITHUB_TOKEN`.
- Политики Actions должны разрешать закреплённые `actions/checkout` и `actions/create-github-app-token`.

### 4. Включение после проверки PR

После ручного слияния этого PR в `main` HOS workflow начнёт работать на следующих push. Само слияние, если оно не меняет книгу, не запустит синхронизацию. Код этой задачи не отправляет dispatch и не выполняет слияние.

## Проверка и диагностика

Локальные проверки не обращаются к API GitHub, не требуют секретов и не меняют настоящую книгу:

```bash
python3 -m unittest -v tests.test_book_sync_dispatch
```

Проверяются посторонние пути, полный push из нескольких коммитов, добавление/редактирование/удаление/переименование, отмена изменений, первый push, более 3000 посторонних файлов, недоступные SHA, HTTP-ошибки и отсутствие повторного запроса при ошибке. Токены в тестах — явно фиктивные значения.

После настройки и слияния:

1. При обычном изменении файла вне книги в Actions HOS ожидается `Book directory unchanged`; шаги App token и dispatch пропущены.
2. При согласованном изменении книги ожидается `Book directory changed`, затем подтверждение принятия dispatch. Ссылку на целевые запуски содержит summary.
3. В [Actions hos-web](https://github.com/Andreevvs/hos-web/actions/workflows/sync-book.yml) проверьте завершение синхронизации и PR. Если сайт уже содержит те же Markdown-файлы, новый PR не должен появиться. Проверяйте реальные изменения книги, не создавайте фиктивные публикации ради теста.

Ошибки обрабатываются с ненулевым кодом выхода; ключи, токены и тела ответов API в диагностику не выводятся:

- **Missing configuration**: добавьте variable и secret под точными именами в HOS.
- **Git operation failed**: отсутствует один из коммитов push. Checkout использует полную историю, но прежний коммит после force-push может быть недоступен. В этом случае dispatch не отправляется. Проверьте историю и при необходимости выполните ручной запуск существующего sync-book в hos-web.
- **401**: проверьте ключ, App ID и срок действия токена.
- **403**: проверьте Actions: write, установку приложения и политики Actions.
- **404**: проверьте доступ App к hos-web и наличие workflow в main; приватный ресурс может давать 404 при отсутствии доступа.
- **422**: проверьте `workflow_dispatch` и наличие ветки main.
- **429/5xx/сетевая ошибка**: проверьте состояние GitHub и целевые запуски. При timeout доставка запроса неопределённа; скрипт не повторяет POST автоматически, чтобы не создавать лишние запуски. Сначала убедитесь, не был ли запуск уже создан, затем используйте ручной запуск или повтор failed job.

Обычный `GITHUB_TOKEN` из HOS не имеет доступа к Actions другого репозитория. Кроме того, изменения книги, отправленные другим workflow с `GITHUB_TOKEN`, обычно не порождают новый запуск по `push`. Для будущей автоматизации такого типа нужно отдельно предусмотреть проверку каталога и вызов dispatcher либо авторство push через подходящий App token. Текущая реализация рассчитана на обычные push/слияния в main и не изменяет другие автоматизации.

# HOS Knowledge Service — Experiment v0.1

Минимальный локальный прототип проверяет два независимых контракта: точное получение
канонического документа и поиск фрагментов с проверяемым provenance. Он читает Markdown
напрямую из Canonical KB и **не** использует `HOS_KB_Runtime.md`.

## Запуск

Требуется Python 3.10+; внешних зависимостей нет.

```bash
python -m unittest discover -v
```

Минимальный программный интерфейс:

```python
from pathlib import Path
from knowledge_service import KnowledgeService

service = KnowledgeService(Path.cwd(), Path("knowledge_service/registry.json"), default_limit=5)
service.build()
service.exact("Экспресс-тест уровня развития v0.1")
service.search("Как в HOS связаны уровни развития и метакомпетенции?", limit=5)
```

`exact(id, version=None)` принимает в качестве версии SHA-256 точных байтов исходного
Markdown. Неизвестный id или SHA возвращает `status: not_found`. `search()` возвращает
настраиваемое число фрагментов. Оба пути сверяют текущий SHA файла с индексом перед
выдачей и явно возбуждают `StaleIndexError` при конфликте.

## Состав и заменяемость

* `FileSourceLoader` читает UTF-8 Markdown и считает SHA-256;
* `MarkdownChunker` сначала делит `fragment`-документы по естественным заголовкам;
* `TfIdfIndex` — заменяемый малый in-memory индекс;
* `KnowledgeService` реализует retrieval и проверку provenance.

Компоненты принимаются через конструктор по небольшим `Protocol`, поэтому loader,
chunker и semantic index можно заменить независимо. Retrieval не зависит от внутренней
реализации индекса.

TF-IDF выбран потому, что он детерминирован, работает офлайн, не требует передачи
Canonical KB внешнему сервису и достаточен для фиксированного запроса эксперимента.
Лёгкая нормализация окончаний — только поисковая техника, не семантическая разметка и
не онтология HOS. Выбор не фиксирует будущую embedding-модель или vector store.

## Область индексации

Индексатор обнаруживает `00 — Индекс HOS.md` и Markdown в активных разделах `01`–`07`.
Остальные корневые документы, `99 — Архив/**`, `07 — Экспорт/**`, runtime-файлы,
двоичные assets и служебный код не индексируются. Явные записи registry имеют стабильные experiment-id и режим retrieval;
остальные активные документы получают хорошо различимый технический `experiment.path.*`
id, вычисленный из пути. Registry — временная инфраструктура, не сущность модели HOS.

## Ограничения Canonical KB, зафиксированные до реализации

1. У документов нет систематических стабильных `id` и `retrieval_mode`; поэтому полный
   стабильный mapping без ручного решения владельца знания невозможен.
2. Статус и версия оформлены неодинаково или отсутствуют в части Markdown.
3. Git не настроен как runtime API, поэтому прототип использует переносимый SHA-256
   точных байтов, а не Git blob SHA.
4. Нет утверждённого словаря синонимов (`метакомпетенции` / `метанавыки`) и эталонной
   разметки релевантности semantic retrieval.
5. Граница активного знания задаётся структурой каталогов и прежними правилами builder,
   но не отдельным машиночитаемым каноническим manifest.

Эти ограничения не исправлялись изменением Canonical KB. Технические path-id для
неявных документов меняются при перемещении; это осознанное ограничение эксперимента,
а не ослабление требования к будущим стабильным id.

## Evals и негативные проверки

`tests/test_knowledge_service.py` автоматизирует E1–E5, включая временную копию для E2,
и отдельно проверяет неизвестный id, пустой query, отсутствующий/переименованный путь,
duplicate id, изменение источника после build и stale provenance при search. Временная
редакция E2 удаляется вместе с temporary directory и Canonical KB не изменяется.

## Архитектурные проблемы

* Надёжный stable id после rename требует авторского registry для всей KB либо будущего
  канонического metadata-контракта; вычислять содержательный id автоматически нельзя.
* Автоматически определить нормативную потребность в `whole_document` для всех будущих
  исполняемых протоколов невозможно. В v0.1 явно закреплён только требуемый экспресс-тест.
* Проверка «практической полезности» поиска пока основана на фиксированном ожидаемом
  наборе источников, а не на экспертно размеченном benchmark с метриками качества.

## Чисто технические решения (не архитектура HOS)

Python, JSON registry, SHA-256, регулярные выражения для Markdown, TF-IDF, простая
нормализация слов, in-memory хранение, размер top-k и формат технических fragment-id —
заменяемые детали эксперимента и не решения содержательной архитектуры HOS.
